Server-Side Cryptographic Ingestion

This maps the internal pipeline execution of the backend on receiving a base64 encrypted payment instruction.

tag
Step 1: Compute SHA-256 Hash of Ciphertext
Generates an immutable fingerprint of the payload block.
key_visualizer
Step 2: Idempotency Claim Check
Atomically queries cache table (ConcurrentHashMap putIfAbsent). Duplicates drop immediately.
vpn_key
Step 3: RSA-2048 OAEP Private Key Decrypt
Unwraps the specific AES symmetric key generated by the sender's phone.
security
Step 4: AES-256-GCM Payload Decryption & Tag Verify
Decrypts data and checks Authentication Tag. Flips trigger decryption failure!
schedule
Step 5: Freshness check (Replay Protection)
Validates that payload was signedAt within the last 24h.
account_balance
Step 6: Atomic Settlement Ledger Entry
Performs SQL Transaction to debit sender, credit receiver, and add a ledger line.

Academic Presentation Study Guide

Hybrid Cryptography Scheme (RSA + AES-GCM)
1. RSA asymmetric algorithms can only encrypt blocks smaller than their key size (e.g. 245 bytes for RSA-2048).
2. Plain text JSON payload is encrypted with a highly efficient symmetric AES-256-GCM key.
3. This AES session key is then encrypted with the Server's RSA Public Key.
4. They are packed together into the MeshPacket.ciphertext.
5. Intermediary nodes route the payload blindly; only the server holds the RSA Private Key to unlock the key and read details.
Deduplication & Idempotency (SHA-256 Gate)
1. When bridges upload mesh packets, duplicates will storm the server concurrently.
2. The backend generates a SHA-256 hash of the ciphertext and attempts to store it in a cache atomically (`putIfAbsent`).
3. The first packet locks the claim, settling the payment. Secondary threads are dropped without decrypting, preventing double debits!
Replay protection
1. Stale capture payloads are blocked via internal encrypted timestamps (`signedAt`) validating packet freshness window.
